# Issue #551：明细级特殊状态设计

## 目标与边界

特殊状态属于单条 `transaction_item`，用于表达报销、退款和统计排除等固定业务语义。它与已经移除的账单自由标签不同：一条明细最多只能有一个状态，用户不能新增、改名或改变状态规则。

本阶段交付设计、受控 UI 组件、Storybook 和组件测试。生产记账页暂不展示可编辑入口，避免用户设置后因保存链路尚未实现而丢失。数据库、保存、查询和统计代码由后续实现 Issue 接入。

## 明细行展示与编辑

- 展示位置复用 `TransactionItemsSection` 金额下方预留区域，以 `TransactionBusinessBadge` 显示状态。
- 无特殊状态时不显示徽标，不保留空白占位。
- 徽标只展示，不单独响应点击。点击明细分类区域仍打开整条明细的编辑弹层，避免同一行出现多个尺寸过小的点击目标。
- 设置入口放在 `TransactionItemPickerDrawer` 内，位于金额与分类操作之后、底部确认按钮之前。它复用 #564 完成的金额前置、分类默认收起结构，不改变分类选择的视觉层级。
- 状态选择器提供“无特殊状态”和 5 个固定状态，使用互斥单选；选择“无特殊状态”即清空状态。

这样能让高频的金额、分类操作保持在上方，也把“编辑一条明细的所有属性”收敛在同一个弹层内。角落徽标不承担编辑职责，因此不会形成难以点击或含义不清的第二入口。

## 操作流程

### 记一笔 / 编辑交易页

1. 账本未启用功能时，不显示特殊状态区域，流程与当前版本完全一致。
2. 账本启用后，用户打开“添加明细”或已有明细的“编辑明细”弹层。
3. 用户填写金额、选择分类，并按需选择一个特殊状态；默认选择“无特殊状态”。
4. 点击“确定”或“保存修改”后，弹层内的受控状态写回当前明细草稿，明细行立即显示对应徽标。
5. 用户再次打开该明细时回填当前状态，可切换其他状态或清空。
6. 后续实现保存链路后，提交整笔交易时与金额、分类一起保存；本设计 PR 不提交任何状态字段。

### 明细列表页

- 行内徽标仅展示状态。
- 点击整行进入现有明细详情 / 编辑流程，再使用相同选择器修改状态，不提供误触风险较高的行内下拉菜单。
- 列表筛选使用页面顶部的“特殊状态”筛选项；筛选结果仍保留原列表行样式。
- 批量修改不纳入第一期，避免误改多条财务记录。

## 账本级开关

- 放置位置：`账本设置` 页面，在“基础信息”之后、“成员”之前新增“明细特殊状态”区块。
- UI：标题、说明、固定状态徽标预览和一个 `Switch`。用户只能启停，不能管理枚举。
- 权限：账本所有者和管理员可修改；普通成员只读，与账本名称、默认货币的权限一致。
- 默认值建议为 `false`，避免功能上线后突然增加所有账本的记账复杂度。
- 关闭时隐藏记账和筛选入口，但不清空已有明细状态；重新启用后恢复展示。这样可逆且不会造成数据损失。

## 数据结构设计

后续 migration 建议为 `transaction_item` 新增：

| 项目            | 设计                                                                            |
| --------------- | ------------------------------------------------------------------------------- |
| 字段名          | `special_status`                                                                |
| PostgreSQL 类型 | 专用 enum `transaction_item_special_status`                                     |
| 枚举值          | `pending_reimbursement`、`pending_refund`、`reimbursed`、`refunded`、`excluded` |
| 默认值          | `NULL`                                                                          |
| 是否可空        | 是；`NULL` 表示无特殊状态                                                       |
| 互斥性          | 单字段天然保证一条明细最多一个状态                                              |

账本级开关建议在账本设置数据中使用 `transaction_item_special_status_enabled boolean NOT NULL DEFAULT false`。枚举由代码和数据库迁移共同维护，不建立用户可编辑的状态表。

前端现有 camelCase 状态仅用于组件 props；后续边界转换应集中映射 snake_case 数据库枚举，避免在组件内散落转换逻辑。

## `excluded` 的统计口径

`excluded` 表示“保留事实记录，但不属于本账本的支出”。规则如下：

- 交易编辑页“本次合计”：排除 `excluded` 支出明细；若同一交易含收入明细，仍按现有净额规则计算其余明细。
- 交易行 / 详情：原始明细金额仍显示，并展示“不计入支出”徽标；交易统计金额使用排除后的有效金额。避免为了统计而隐藏原始记录。
- 月度汇总、分类统计、趋势、预算消耗、Dashboard 支出合计：全部排除 `excluded` 支出金额。
- 现金流 / 账户余额：第一期也排除，保持“这不是我的支出”的产品语义一致。若未来要表达“账户真实出账但不计消费”，应另行设计“消费统计金额”和“账户流水金额”两个口径，不能在本状态上暗含第二套规则。
- `excluded` 不改变收入统计。后续服务端校验应限制它只用于支出明细，避免产生无定义的收入语义。
- 待报销、待退款、已报销、已退款仅改变状态分组，不自动改写原明细金额或统计结果；报销 / 退款本身仍应由真实收入或冲销记录表达。

## 筛选与分组

- 交易 / 明细列表的筛选弹层新增“特殊状态”多选项：无特殊状态、待报销、待退款、已报销、已退款、不计入支出。
- 同一筛选维度内为 OR，不同维度间沿用现有 AND 规则。例如“餐饮 + 待报销”只返回餐饮类且待报销的明细。
- 默认列表仍按时间分组，不因启用功能改变。用户主动选择“按特殊状态分组”后，顺序为：待报销、待退款、已报销、已退款、不计入支出、无特殊状态。
- 分组标题展示明细条数和该组有效金额；`excluded` 组金额显示原始金额，并明确标注“不计入合计”。
- 筛选与分组的计算对象必须是明细，而不是整张交易；同一交易命中部分明细时只统计命中明细金额，避免重现自由标签的统计失真。

## 空、加载与错误状态

- 空状态：选择器始终有固定枚举，“空”指当前值为 `NULL`，显示并选中“无特殊状态”；明细行不显示徽标。筛选无结果时复用页面 `EmptyState`，提示清除特殊状态筛选。
- 加载状态：选择器和账本开关显示 MUI `CircularProgress` 与说明文案，禁用交互；列表页复用现有 skeleton，徽标位置不额外闪烁。
- 错误状态：组件内显示安全、可理解的错误提示和“重试”入口；已有明细内容仍保留，不用 URL 参数传递错误，也不因状态读取失败隐藏整条明细。
- 保存失败：后续接入时沿用 `BaseActionState` 和 `FailureFeedbackDialog`，保留弹层草稿供用户重试。

## 组件拆分

- `TransactionBusinessBadge`：固定状态视觉和文案的唯一来源。
- `TransactionSpecialStatusSelector`：受控的互斥选择器，负责空 / 加载 / 错误状态。
- `TransactionItemPickerDrawer`：后续实现阶段组合金额、分类和状态选择器；不拥有持久化逻辑。本 PR 不修改该文件，避免与 #567 的动态快捷入口并行改动冲突。
- `TransactionItemsSection`：仅在明细摘要包含状态时展示角落徽标。
- `LedgerSpecialStatusSetting`：受控账本开关、权限只读和加载 / 错误反馈。
- 后续页面 hook / Service：负责加载开关、草稿回填、保存和边界枚举转换。

## Storybook 与组件测试覆盖

- 5 种徽标、无特殊状态、明细行全部状态和空明细。
- 选择器可交互切换 / 清空、加载、错误与重试。
- 状态选择器按 #564 后弹层宽度和信息层级设计；后续接入时放在分类操作与底部确认按钮之间。
- 账本开关启用、关闭、普通成员只读、加载、错误与重试。
