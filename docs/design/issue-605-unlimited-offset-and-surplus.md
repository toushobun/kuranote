# Issue #605：退款 / 报销无限关联与超额收入（#1078 最新口径）

## 背景

#598 建立关联机制，#606 将退款与报销统一为收入侧单目标模型。#605 解除关联总额不得超过原支出的限制。原方案曾把“倒赚”记为**原支出的负业务净额**、并派生 `reimbursement_surplus` 状态；该方案已被 **#1078（2026-11-13）取代**。

## 关联金额与实际抵消

退款或报销关联写入**收入明细原金额**，不按剩余额度截断，同一原支出可关联多笔收入。与原始关联金额不同，**实际抵消**有总上限：同一原支出的实际累计抵消最多等于原支出原金额。

所有有效关联按以下键统一排序；退款与报销进入同一个序列：

1. 收入记录的 `transaction_at`；
2. 收入记录的 `created_at`；
3. 关联收入明细的 `sort_order`；
4. 关联收入明细的 `id`。

金额为 0 的关联保留关联角色，但不占额度，不参与抵消分配。只有目标支出记录与关联收入记录均为 `active` 时才参与核销。更改金额、时间、原目标、删除或作废关联后，视图按现存有效关联重新计算先后顺序，不记录一份可能过期的静态分配结果。

对序列中某个金额为 `x` 的关联，若在它之前已关联的总金额为 `previous`，原支出金额为 `base`：

```text
applied = min(x, max(base - previous, 0))
surplus = x - applied
```

总额遵循两套不同的字段口径：

- `refunded_amount`、`reimbursement_amount` 与 `calculate_transaction_item_remaining_offset_amount` 继续表示**原始关联累计金额**。其中 `remaining_offset_amount = base - Σ原始有效关联金额` 可以为负。这是供候选剩余提示、未保存编辑和原始关联展示使用的状态值，不是收入归属。
- `transaction_item_with_refund.business_net_amount` 是**实际业务净额**。原支出为 `max(base - Σ实际抵消金额, 0)`；退款 / 报销收入明细为 `原收入金额 - 本明细实际抵消金额`。普通明细保持原规则。

例如原支出 A=980；B（同一退款记录的两条明细）=980、1,000；C（较晚退款记录）=1,000。结果为 A 业务净额 0、B 的两条分别为 0 和 1,000、C 为 1,000。

## 报销状态机

已进入报销流程的原支出仅派生两种有效状态：

- **`pending_reimbursement`**：原始累计关联金额尚不足以抵消原支出；
- **`reimbursed`**：累计关联金额已达到或超过原支出，表示已结清。

PostgreSQL 无法安全地从已有枚举中直接删除 `reimbursement_surplus` 标签，所以数据库枚举中暂时保留此旧值，但新关联、状态重算与受控编辑都不再派生它。本项目上线前不做旧数据自动迁移或兼容逻辑。普通仅退款原支出的 `special_status` 继续为 `NULL`，显示层可根据关联金额及剩余值展示「已退款」。

## 统计与展示

统计不再把原支出的负业务净额反转计入收入桶。原支出抵至 0 后保持在其原支出分类；超额收入按**发生的退款 / 报销收入明细本身**的 `transaction_at`、类别、账户等维度统计。净额依靠业务金额字段，避免双重计算。

原支出 A 列表显示净额 0、状态「已退款」「已报销」或混合的「已结清」，**不出现「已倒赚」**。有超额收入的退款 / 报销列表金额显示其业务净收入（例：`+¥1,000`），原有「退款收入」「报销收入」标签保留，另显示「倒赚 ¥1,000」，沿用原先业务倒赚配色。

编辑 / 详情小票对每条关联明细显示实际抵消额，例如「抵消原支出 ¥980」；无可抵消额度时显示「原支出已抵完」；超额金额下展示「倒赚 ¥X」。整个小票的净额按业务净额（收入为正）展示，有倒赚时解释原退款 / 报销合计、实际抵消、倒赚金额。新建明细抽屉按含未保存小票更改的剩余额度实时提示超额。

## Picker 与编辑

无限关联不等于取消合法性限制：退款 / 报销仍要求原支出与收款账户币种一致。已结清和有超额收入的原支出仍可选；剩余额度非正时，默认金额不自动带出。关联变更或收入记录改日期触发重新分配；编辑确认和统计预览均应按新业务净额展示。
